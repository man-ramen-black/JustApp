# 스쿼시 스킬

스쿼시는 `git reset --soft` + 재커밋으로 수행한다(interactive rebase는 이 환경에서 쓸 수 없다). 재커밋은 author date를 현재 시간으로 새로 찍으므로 **원래 author date를 보존하는 것**이 이 스킬의 핵심이다.

## 핵심 원칙

- **범위를 지정했는지로 갈린다.** 개수(`최근 2개`)·위치(`HEAD~3까지`)·그룹(`테스트와 기능으로 나눠`) 중 하나라도 말했으면 지정이다. super-flow처럼 상위 절차가 시작 HEAD를 정해 둔 경우도 지정으로 본다.
    - 지정했으면 되묻지 말고 수행한다. 대상 커밋의 제목·본문을 고쳐야 한다는 사실은 반대할 근거가 아니다(스쿼시는 메시지 재작성을 포함한다).
    - 미지정이면 1단계의 목록·그룹 제안까지만 하고 승인을 기다린다. "스쿼시해줘"는 의사 표시일 뿐이고, 브랜치 문맥상 대상이 자명해 보여도 같다.
- **백업 필수**: reset 전에 현재 HEAD를 가리키는 백업 브랜치를 만든다(2단계).
- **author date 보존 필수**: reset 전에 범위에서 가장 오래된 커밋의 author date를 캡처하고, 모든 재커밋에 `git commit --date`로 같은 값을 적용한다. `--date`는 author date만 바꾸고 committer date는 현재 시간으로 둔다.
- **다른 브랜치의 조상이 된 커밋, 이미 push된 커밋, 머지 커밋은 범위에 넣지 않는다.** 재작성하면 같은 내용이 두 해시로 남고, 머지를 평탄화하면 어느 브랜치의 작업인지가 히스토리에서 사라진다. 걸리는 커밋이 있으면 그 위에서 끊어 범위를 좁히고, 남는 구간이 2커밋 미만이면 합칠 것이 없다고 알리고 멈춘다.
    ```
    git branch -a --contains <범위에서 가장 오래된 커밋>   # 현재 브랜치 외가 나오면 범위 밖
    git log --oneline origin/<현재 브랜치>..HEAD          # 여기 없는 범위 커밋은 이미 push됨
    ```
    원격에 같은 이름의 브랜치가 없으면 두 번째 명령은 실패하며, 그때는 push된 커밋이 없는 것이다.
- **스펙·플랜 문서(`docs/superpowers/`)는 어느 그룹에도 넣지 않는다.**

## 1단계: 범위(base) 결정

- 사용자가 범위를 지정했으면 그대로 쓴다(예: 최근 N개 → `HEAD~N`).
- **미지정이면 승인 게이트를 거친다(필수).**
  1. base는 이 브랜치가 분기한 지점이다. 작업 브랜치는 `release`에서 분기하므로 `git merge-base HEAD release`를 기본으로 쓰고, `origin/release`·`master`의 merge-base와 비교해 HEAD에 가장 가까운(`git rev-list --count <merge-base>..HEAD`가 가장 작은) 것을 고른다. 판단이 모호하면 사용자에게 base를 묻는다.
  2. 아래 표를 제시한다. 커밋을 가리키는 모든 자리에는 **해시와 제목을 함께** 적는다(`57dfd60 테스트: TextEditor ...`). 해시만 적으면 사용자가 커밋마다 `git show`를 다시 돌려야 한다.
     - 작업 이력 표 `# | 작업 | 현재 커밋`: 이 브랜치에서 무엇을 하고 그다음 무엇을 했는지 시간순으로 적는다. 리뷰 반영·재작업처럼 앞 작업을 고친 항목은 그 사실을 적는다.
     - 기존 커밋 표 `커밋 | 카테고리 | 제목 | 파일`
     - 그룹 제안 표 `그룹 | 카테고리 | 제목(안) | 포함 커밋 | 묶은 이유`
  3. 승인을 받은 뒤에만 2단계 이후로 진행한다. 리스트업 턴에서는 히스토리를 바꾸는 명령(`branch`·`reset`·`rebase`·`commit`·`cherry-pick`)을 실행하지 않고 조회(`log`·`show`·`diff`·`merge-base`·`rev-list`)만 한다.

### 그룹 구성 기준

- 분할·합침 판단과 카테고리는 `commit` 스킬을 그대로 따른다.
- **같은 대상을 반복 수정한 연쇄는 한 그룹이다.** `추가 → 돌려 보니 안 되어 수정 → 리뷰 지적 수정`처럼 뒤 커밋이 앞 커밋이 만든 것을 고치면, 뒤가 구조 정리 성격이어도 앞과 묶는다. 판단 기준은 "뒤 커밋을 되돌리면 앞 커밋이 불완전해지는가"이다.
- 원본과 1:1인 안은 제안하지 않는다(그룹 수가 같으면 스쿼시할 이유가 없다). 서로 독립적으로 성립하는 작업(기능·테스트·규칙 문서 등)은 한 덩어리로 뭉치지 않는다.

## reset 직전 재확인 (필수)

- `git log --oneline <base>..HEAD`로 대상 커밋이 확인 때와 같은지 다시 본다. 늘어난 커밋이 있으면 어느 그룹에 넣을지 사용자와 정한 뒤 진행한다.
- `git status --porcelain`으로 **범위 밖 파일이 수정 상태로 떠 있는지** 본다. reset 뒤의 `git add`는 작업트리 내용을 스테이지하므로, 다른 세션의 미커밋 편집이 내 커밋에 실린다. 떠 있으면 스크래치패드에 복사해 두고 `git checkout <백업 브랜치> -- <파일>`로 되돌린 뒤 스쿼시하고, 끝나면 복사분을 되돌린다.
- 파일 목록을 셸 변수에 담아 루프를 돌리지 않는다. zsh는 변수 확장 시 단어를 나누지 않아 루프가 빈손으로 돌고 종료 코드는 성공으로 나온다. 파일은 명령마다 직접 나열한다.

## 2단계: 백업 브랜치 생성

브랜치명의 `/`를 `-`로 바꿔 `backup/<브랜치명>-pre-squash`로 만든다. 같은 브랜치에서 두 번째부터는 `-2`·`-3`을 붙인다.

```
git branch backup/feature-usage-timer-compose-pre-squash HEAD
```

생성한 백업 브랜치명을 사용자에게 알린다. 잘못되면 `git reset --hard <백업 브랜치>`로 복구한다.

## 3단계: author date 캡처

```
git log --reverse --format=%aI <base>..HEAD | head -1
```

## 4단계: soft reset + 재커밋

```
git reset --soft <base>
git restore --staged .
# 그룹마다 반복
git add <그룹 파일들>
git commit --date="<캡처한 author date>" -m "..." -- <그룹 파일들>
```

- 메시지는 `commit` 스킬로 새로 쓴다. 기존 메시지를 이어 붙이거나 제목만 다듬어 재사용하지 않는다.
- 합칠 커밋들이 서로 떨어져 있고 그 사이에 다른 그룹 커밋이 끼어 있으면 soft reset으로 격리할 수 없다. 가장 오래된 대상 커밋 바로 아래로 `git reset --hard`한 뒤, 대상 커밋들을 `git cherry-pick --no-commit`으로 누적해 1커밋으로 만들고(`--date` 적용), 사이에 있던 커밋은 `git cherry-pick`으로 뒤에 복원한다. 옮기는 커밋끼리 파일이 겹치면 순서를 바꾸지 말고 사용자에게 알린다. `reset --hard`는 미커밋 변경을 지우므로 먼저 보존한다.

## 5단계: 검증 후 백업 처리

```
git diff --quiet HEAD <백업 브랜치> && echo "OK: 유실 없음" || git diff --stat HEAD <백업 브랜치>
git log --format="%h | a:%ai | c:%ci | %s" <base>..HEAD
git status
```

- 트리가 백업과 동일하고(스쿼시는 커밋만 재구성하므로 최종 트리가 같아야 한다) author date가 보존됐으며, 범위를 사용자가 지정했거나 승인했으면 백업을 삭제한다: `git branch -D <백업 브랜치>`
- 그 외에는 백업을 남기고 "결과가 의도대로면 `git branch -D`, 아니면 `git reset --hard`로 복구"를 안내한다.
- 이미 push된 커밋을 재작성했다면 force push가 필요하다는 사실만 알리고, push는 명시적으로 지시받았을 때만 한다.

## 금지

- `--date` 없이 재커밋하지 않는다.
- `--no-verify`·`git rebase -i`를 쓰지 않는다.
