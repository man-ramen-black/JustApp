# 규칙·스킬 편집

## 어디까지 하는가

| 편집 | 절차 |
|:---|:---|
| 발동 조건·판정 기준·금지 사항이 바뀐다 | 아래 전부 |
| 문구 정리·경로 갱신·오탈자 | 압축 + 정적 점검만 |

판정이 바뀌지 않는 편집에는 비교 실행(검증 ②)을 하지 않는다.

## 어디에 두는가 (쓰기 전에 판정)

자리는 "누가 그것을 읽어야 하는가"로 고른다.

| 규칙의 성질 | 자리 |
|:---|:---|
| 모든 작업에 적용되는 프로젝트 컨벤션 | 저장소 `CLAUDE.md`. 모든 세션에 주입되므로 기존 형식대로 한 줄로 쓴다 |
| 특정 파일(ViewModel·DataStore 등)을 다룰 때만 필요 | `.claude/rules/<주제>.md` + `paths` frontmatter. 그 파일을 Read·Write·Edit할 때 자동 로드되므로, 새 파일을 만드는 작업이 놓치지 않게 `CLAUDE.md`에 위치를 한 줄 남긴다 |
| 다른 문서가 가리킬 때만 읽히는 판정 기준·환경 사실·근거 | `.claude/references/<주제>.md`. 가리키는 문서가 없으면 읽히지 않으므로 그 일을 시키는 스킬이나 `CLAUDE.md`에 위치를 한 줄 남긴다 |
| 특정 작업(커밋·테스트 작성·Compose 화면 등)을 할 때만 필요 | 그 작업의 `.claude/skills/<스킬>/SKILL.md`. description이 발동 조건이다 |
| 사람이 `/이름`으로 부르는, 단계가 있는 절차 | `.claude/commands/` |
| 기계적으로 판정할 수 있고 매번 지켜야 하는 것 | `.claude/hooks/` + `.claude/settings.json` |
| 사용자 개인 선호·작업 스타일 | auto-memory |
| 이 기계에서만 참인 것(개인 환경 이름·홈 디렉터리 상태) | 사용자 레벨 `~/.claude/` |

**auto-memory를 규칙으로 옮겨도 메모리는 그 브랜치가 release에 머지된 뒤 지운다.** 먼저 지우면 머지 전까지 release에서 시작하는 세션에 어느 쪽도 실리지 않는다. 옮길 때 메모리 본문 끝에 `규칙 이동: <브랜치>` 줄을 남기면 `merge` 스킬이 머지 후 그 메모리를 지운다.

**문서를 고치러 들어간 자리에서 그 문서의 자리가 맞는지도 함께 본다.** 어긋난 자리는 새로 만들 때보다 고칠 때 드러난다. 옮기면 그 경로를 가리키는 문자열도 함께 고친다.

## 압축

- 규칙을 추가하는 같은 편집에서 압축한다. 추가만 하고 미루면 그 파일은 계속 늘어난다.
- 덜어낼 후보: 앞 문장이 이미 말하는 재진술, 여러 문서에 같은 근거를 다시 적은 것, 같은 얘기를 두 번 하는 사례(사례는 하나까지).
- 남길 것: 실측으로만 알 수 있는 함정과 그 수치, 임계값·대기값을 그 값으로 정한 근거, 코드 샘플이 있어야 올바르게 적용되는 규칙의 샘플.
- 간결함 때문에 규칙이 모호해지면 안 된다. 판단이 갈릴 수 있는 규칙은 금지 예시와 허용 예시를 한 쌍으로 둔다.

## 검증

**① 정적 점검 (항상)**

```bash
grep -rn "<새 규칙의 핵심 어휘>" .claude/ CLAUDE.md   # 같은 규칙·근거가 이미 있는지
git diff --stat                                      # 분량 변화
```

- 인용한 스킬·스크립트·함수·클래스·경로는 실물을 확인한다. 없는 이름을 규칙에 적으면 그 규칙을 따르는 세션이 전부 헤맨다.
- 고친 문장을 다른 문서가 가리키고 있으면 그 참조도 함께 고친다. 개수 단어(`아래 넷`)와 다른 문서에 베껴 둔 값도 같다. 바뀐 판정의 **반대말**로도 검색한다(`자동`↔`요청`, `한다`↔`하지 않는다`). 같은 결론을 제 문장으로 적어 둔 다른 문서는 어휘 검색에 걸리지 않는다.
- 식별자를 일괄 치환했으면 뒤에 붙은 한국어 조사(은/는, 이/가, 을/를)가 받침에 맞는지 본다.
- 훅·스크립트를 고쳤으면 고치기 전 사본(`git show <편집 전 SHA>:<경로>`)과 같은 입력으로 돌려 결과를 대조한다. 새 버전만 돌리면 기존 판정이 조용히 무력화된 것을 알 수 없다.

**② 발동 검증 (발동 조건·판정이 바뀐 규칙마다)**

그 규칙이 개입해야 하는 최소 시나리오를 처리군(규칙 있음)과 비교군(규칙 없음)에 같은 질의로 4회씩 돌려, 처리군만 그 판정을 내리는지 본다. 수단은 `scripts/rule-ablation.py`다. `claude -p --safe-mode`가 저장소 규칙 없이 넘긴 사본만 싣기 때문에 `CLAUDE.md`에도 비교군을 만들 수 있다. 서브에이전트는 `CLAUDE.md`와 작업 트리 파일을 그대로 보므로 비교군으로 쓰지 않는다.

```bash
# 비교군: 새 규칙은 그 문장을 뺀 사본, 강화한 규칙은 편집 전 사본(git show <편집 전 SHA>:<문서> > before.md)
python3 .claude/skills/rule-edit/scripts/rule-ablation.py drop <문서> <시작-끝> --out <스크래치패드>/minus.md
python3 .claude/skills/rule-edit/scripts/rule-ablation.py run --variant full=<문서> --variant minus=<스크래치패드>/minus.md --query <질의.md> --out <결과.md>
```

- 질의 파일에는 어떤 답이면 갈린 것인지를 `기대:` 줄로 실행 전에 적는다. 스크립트는 그 줄을 모델에 보내지 않고, 없으면 거부한다.
- 새 규칙은 **위반을 유도하는** 요청으로 만들고 판정 근거 문장을 인용시킨다. 처리군이 옛 문구를, 비교군이 새 문구를 인용한 회차는 버린다.
- 결과를 본 뒤 새로 짠 질의는 판정에 넣지 않고 첫 질의 결과로 판정한다. 질의를 바꿔 가며 갈리는 쪽을 찾으면 어떤 규칙도 남는다.
- 단계를 추가하거나 옮겼으면 문서 전문을 주고 "이 절차를 순서대로 따르면 어느 단계에서 X를 하는가"를 물어, 그 단계에 실제로 도달하는지 따로 본다.
- 스킬 description을 바꿨으면 발동률을 잰다. skill-creator 스킬 디렉터리에서 `python3 -m scripts.run_eval --eval-set <질의.json> --skill-path <스킬 디렉터리>`로 부른다(스크립트 경로로 직접 부르면 `ModuleNotFoundError`).
- 금지 규칙은 실제로 어기게 해야 검증되고 그 부작용이 크므로 정적 점검까지만 하고 미검증으로 보고한다.

**발동하지 않으면 문구를 다듬기보다 자리를 옮긴다.** 산문 규칙은 그 자리에서 규칙을 찾아볼 이유가 없는 작업에는 개입하지 못한다.

- 실제 작업에서 위반이 반복됐다면 그 시점에 이미 도는 절차(훅·스킬 체크리스트)에 판정을 넣고 산문에는 한 줄만 남긴다.
- 판정이 갈려야 하는 규칙인데 처리군과 비교군이 같게 나오면(효과 미관측) 그 추가를 되돌린다.
- 드물게 크게 터지는 일을 막는 규칙은 비교군도 평소에 그 행동을 하지 않아 늘 같게 나온다. 대조 대신 그 규칙을 만든 실제 사고(날짜와 커밋·대화 자리)를 지목하고, 지목하지 못하면 되돌린다.
- 되돌렸으면 응답에 `철회: <파일> <항목>(<판정>)`으로 알린다. 사용자는 그 규칙이 살아 있다고 믿고 판단한다.

**③ 기존 규칙 회귀 (수정한 파일마다)**

그 파일이 소유한 기존 판정을 뽑아 여전히 발동하는지 본다. 훅이 있으면 훅을 직접 돌려 보는 것이 가장 값싼 회귀다.

## 검증 범위 상한 (넘기지 말고 그대로 보고한다)

| 대상 | 할 수 있는 것 | 할 수 없는 것 |
|:---|:---|:---|
| 저장소 안에서 끝나는 절차(`commit`·`squash`) | 임시 브랜치에서 전체 절차 실행 | 없음 |
| 테스트 작성 스킬(`unit-test`) | 산출 코드 실행·통과 확인 | 없음 |
| 기기가 필요한 스킬(`ui-test`·`compose`의 계측 테스트) | 발동 여부, 산출 코드 형태·컴파일 확인 | 기기 없는 환경에서의 실행 |
| `CLAUDE.md` 규칙 | `rule-ablation.py` 비교군(그 문장을 뺀 사본) | 저장소·브랜치 맥락에서 발동하는 규칙의 판정 차이(저장소 밖에서 돈다). `-p` 실행에는 묻지 않고 진행하라는 지시가 실려 묻기·진행 판정도 갈리지 않는다 |
| 금지 규칙 | 정적 점검 | 위반을 실제로 유발하는 검증 |
| 장치·절차 규칙(단계 순서·정리 시점처럼 한 턴 질의로 효과가 드러나지 않는 것) | 정적 점검, 도달 확인 | 비교 실행. 미검증으로 적고 재발했을 때 보일 신호를 함께 적는다 |

미검증으로 남긴 항목은 사유와 함께 응답에 적는다. 적지 않으면 다음 세션이 검증된 것으로 오인한다.
