# super-flow

새 기능 개발의 출발점. 아래 **적용 규칙**을 컨텍스트로 삼아 `superpowers:brainstorming` 스킬을 호출한다. brainstorming은 설계 → 계획(`superpowers:writing-plans`) → 구현 → 완료로 자연스럽게 이어지며, 아래 규칙은 그 전 과정에 적용된다.

이 스킬을 호출한 에이전트가 규칙을 직접 수행하는 것이 아니라, **brainstorming과 그 이후 흐름이 이 규칙대로 동작하도록** 규칙을 전달하는 것이 핵심이다.

## 동작

1. 사용자의 기능 요청을 그대로 brainstorming의 입력으로 삼는다.
2. 아래 "적용 규칙"을 brainstorming 호출 시 컨텍스트로 함께 전달한다.
3. `superpowers:brainstorming` 스킬을 호출한다. 이후 흐름(계획 → 구현 → 검증 → 스쿼시)은 이 규칙을 따라 진행된다.

## 적용 규칙

brainstorming부터 기능 완성까지 다음 규칙을 지킨다. 이 규칙들은 하위 스킬의 기본 동작보다 우선한다.

1. **권장안 자동 채택** — 권장안이 있는 결정은 사용자에게 묻지 않고 권장안으로 진행한다. 어떤 결정을 권장안으로 정했는지는 한 줄로 알린다. 의도·요구사항이 모호해 권장안조차 세울 수 없을 때만 질문하며, 부득이 질문할 때는 PushNotification으로 알린다.

2. **서브에이전트 활용** — 구현은 태스크별 서브에이전트로 진행한다(`superpowers:subagent-driven-development`). 탐색·검토 등 독립적인 작업도 서브에이전트로 진행한다.

3. **설계·계획 문서는 .md로 생성하되 커밋 금지**
   - 설계 문서를 마크다운(`.md`) 파일로 만든다: `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`. 이 설계 문서에는 **"이후 `superpowers:writing-plans` 스킬로 계획을 진행한다"**는 내용을 포함한다.
   - 계획 문서도 마크다운(`.md`) 파일로 만든다: `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`.
   - 두 문서 모두 워킹 트리에 생성만 하고 **`git add`·커밋하지 않는다.** 하위 스킬이 문서를 커밋하라고 안내해도 그 단계는 건너뛴다. 이후 모든 커밋·스쿼시에서도 이 경로(`docs/superpowers/specs`, `docs/superpowers/plans`)는 제외한다.

4. **테스트 코드로 검증** — 기능 구현 후 테스트 코드로 검증한다. 테스트 코드를 작성할 때는 **`ui-test` 스킬을 필수로 참고**한다(저장소 테스트 컨벤션). 작성에 그치지 말고 실제로 실행해 통과를 확인한 뒤에만 완료로 넘어간다(`superpowers:verification-before-completion`).

5. **완료 후 커밋 스쿼시** — 모든 작업이 끝나면 구현 중 쌓인 커밋들을 정리된 커밋으로 스쿼시한다. 단, 하나의 커밋으로 몰지 않고 변경 성격(기능·테스트·리팩터링 등)에 따라 여러 커밋으로 나눠 스쿼시한다. 커밋 메시지·분류는 **`commit` 스킬을 참고**한다. 설계·계획 문서는 스쿼시 결과에 포함하지 않는다.
