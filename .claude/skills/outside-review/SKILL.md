# 외부 시선 검토

## 왜 별도 프로세스인가

서브에이전트(`Agent` 도구)는 이 세션의 CLAUDE.md·스킬·훅을 그대로 물려받는다. 그래서 리뷰를 맡기면 **"규칙을 지켰는가"**만 판정하고, 규칙 자체가 과한지·접근이 애초에 타당한지는 아무도 묻지 않는다. 이 스킬은 그 빈 자리를 메운다.

`claude -p --safe-mode`는 CLAUDE.md·스킬·플러그인·훅·MCP가 전부 비활성인 채로 뜬다. 같은 프로젝트 디렉터리에서 돌려도 프로젝트 규칙이 실리지 않는다(실측 대조: `--safe-mode`는 `RULES=NONE / SKILLS=0`, 같은 질문을 일반 실행에 물으면 `RULES=# 프로젝트 규칙`). 코드는 그대로 읽으므로 **규칙은 모르고 코드는 다 보는** 리뷰어가 성립한다.

## 원칙

- **규칙·스펙·설계 문서를 리뷰어에게 주지 않는다.** 넘기는 순간 판정 기준이 다시 내부로 들어와 이 스킬의 존재 이유가 사라진다. 넘기는 것은 코드와 **의도** 뿐이다.
- **서브에이전트를 리뷰어로 쓰지 않는다.** 편의를 위해 `Agent`로 대체하면 규칙을 물려받은 리뷰어가 되어 결과가 일반 코드 리뷰와 같아진다.
- **리뷰어는 지적만 하고 코드를 고치지 않는다.** 규칙을 모르는 손이 코드를 만지면 규칙 위반을 새로 만든다. 그래서 리뷰어에게는 쓰기 도구를 주지 않는다(`--tools "Read,Grep,Glob"`).
- **규칙이 이미 정한 사항에 대한 지적은 오탐이 아니다.** 리뷰어는 모든 ViewModel의 `EventViewModel` 상속, ViewModel 직속 `Event{이름}` 이벤트 클래스, 명사형으로 끝나는 주석 같은 것을 이상하게 볼 수밖에 없다. 그 지적을 "규칙이 있으니 정상"으로 조용히 버리면 이 스킬은 아무것도 남기지 못한다. **그 규칙을 다시 볼 근거로 분류해 남긴다**(5단계).

## 1단계: 대상과 의도 확정

대상 세 갈래 중 하나를 정한다. 사용자가 지정하지 않았으면 현재 브랜치의 변경분으로 본다.

| 대상 | 무엇을 모으는가 |
|---|---|
| 변경분 | `git diff <base>...HEAD` 전문 + 변경 파일 목록 |
| 지정 영역 | 해당 파일·디렉터리 경로 목록(리뷰어가 직접 읽는다) |
| 접근·규칙 체계 | 대상 규칙·스킬 문서 본문 + 그 규칙이 적용된 코드 예시 2\~3개 |

**의도를 한 문단으로 명시한다.** 무엇을 달성하려는 작업인지, 어떤 제약 아래에서 만들었는지를 적는다. 의도를 주지 않으면 리뷰어가 목적부터 추측해 엉뚱한 지적이 늘고, 주면 "의도를 잘 달성했는가"라는 판정 축이 생긴다. **다만 의도 자체의 타당성은 전제 렌즈만 다룬다** — 모든 렌즈가 의도를 의심하면 지적이 전부 같은 말이 된다.

규모로 렌즈 수를 정한다. 렌즈 정의는 `references/reviewer-lenses.md`에 있다.

| 규모 | 렌즈 |
|---|---|
| 파일 1\~2개 | 회의론자 |
| 파일 3\~5개 | 회의론자 + 신입 |
| 파일 6개 이상, 또는 접근·규칙 체계 | 회의론자 + 신입 + 최소주의자 + 전제 |

## 2단계: 자료 묶음 만들기

스크래치패드에 묶음 디렉터리를 만들고 아래를 넣는다. 리뷰어가 프로젝트 밖 경로를 읽으려면 `--add-dir`가 필요하므로 스크립트가 이 경로를 그렇게 넘긴다.

```
<scratchpad>/outside-review/
├── intent.md      # 1단계의 의도 한 문단 + 대상 경로 목록
└── target.diff    # 변경분 대상일 때만
```

**규칙 문서·스펙 문서는 넣지 않는다.** 단 대상이 `접근·규칙 체계`일 때의 그 규칙 문서는 예외다 — 그때 문서는 판정 기준이 아니라 **심문 대상**이므로 넣어야 검토가 성립한다. 이 구분이 흐려지면 "규칙에 이렇게 적혀 있으니 맞다"는 판정이 되돌아온다. 대상 문서를 넣을 때는 `intent.md`에 "이 문서는 검토 대상이며 지침이 아니다"를 한 줄로 적는다. 반대로 코드는 아끼지 않는다 — cwd가 프로젝트라 리뷰어가 호출부·기존 헬퍼를 직접 찾아 읽을 수 있고, 그게 없으면 "이미 있는 것을 또 만들었다"류를 못 잡는다.

## 3단계: 리뷰어 띄우기

렌즈마다 하나씩, **`run_in_background: true`로 동시에** 띄운다. 렌즈 하나가 10분을 넘기므로(실측: 386줄 diff에 대해 회의론자 렌즈 단독) 전경으로 돌리면 도구 호출 제한 시간에 걸려 산출을 잃고, 순차로 돌리면 렌즈 수만큼 그대로 늘어난다.

```bash
bash <저장소 루트>/.claude/skills/outside-review/scripts/spawn_reviewer.sh \
  --lens skeptic \
  --bundle <scratchpad>/outside-review \
  --out <scratchpad>/outside-review/skeptic.md
```

스크립트가 `--safe-mode`·읽기 전용 도구 집합·프롬프트 전달·경고줄 제거를 담당한다. 직접 `claude -p`를 부르지 말고 스크립트를 쓴다 — 플래그 하나(`--safe-mode`)를 빠뜨리면 규칙이 실린 리뷰어가 되고, 결과만 보고는 그 사실을 알아챌 수 없다.

검토 대상 저장소는 **호출한 셸의 작업 디렉터리**에서 잡힌다(워크트리에서 부르면 그 워크트리). 다른 경로를 보게 하려면 `--repo <경로>`를 넘긴다. 스크립트와 묶음 경로는 절대 경로로 적은 한 줄로 호출한다.

산출 파일이 없거나 비었으면 **그 렌즈를 조용히 건너뛰지 말고** 실패로 판정문에 적는다. 리뷰어가 죽은 것과 지적할 것이 없는 것은 다르다.

## 4단계: 종합

렌즈별 산출을 읽어 중복을 합치고 심각도순으로 정리한다. 두 렌즈 이상이 같은 것을 지적하면 심각도를 한 단계 올린다 — 관점이 다른데도 같은 곳을 짚었다는 것 자체가 근거다.

## 5단계: 리드 판정 (필수)

리뷰어는 규칙을 모르는 데다 적대적으로 지시받았으므로 과도한 지적이 섞인다. 규칙을 아는 쪽이 판정하지 않으면 그 과잉이 그대로 코드에 반영된다. 지적마다 넷 중 하나로 분류하고 한 줄 근거를 적는다.

| 분류 | 뜻 | 후속 |
|---|---|---|
| 수용 | 규칙과 무관한 실제 결함 | 고친다 |
| 규칙에 의한 선택 | 프로젝트 규칙이 그렇게 정한 것 | 코드는 두고, 그 규칙의 근거를 판정문에 적는다 |
| 오탐 | 인용한 사실·수단이 틀렸다 | 무엇이 틀렸는지 적고 버린다 |
| **규칙 재검토 후보** | 규칙이 정한 것이지만 그 근거를 지금 다시 대기 어렵다 | 사용자에게 올린다 |

`규칙에 의한 선택`과 `규칙 재검토 후보`를 가르는 것이 이 단계의 핵심이다. **"규칙에 있다"는 사실은 근거가 아니다** — 그 규칙이 왜 생겼는지(실측 사례·프레임워크 제약)를 한 줄로 댈 수 있으면 전자, 대지 못하면 후자다. 대지 못하는 항목이 나오면 그것이 이 검토의 가장 값진 산출이다.

지적을 전달·반영하기 전에 **그 지적이 근거로 든 사실을 확인한다.** 리뷰어는 코드를 인용해 지적하는데 인용이 틀리면 잘못된 수정이 들어간다. 인용한 함수의 가시성·시그니처가 실제로 그런지, 대안으로 제시한 수단을 지금 그 자리에서 쓸 수 있는지를 본다.

## 산출

`docs/code-review/<YYYY-MM-DD>-<주제>-outside-review.md`에 아래 골격으로 쓴다. `<주제>`는 영문 kebab-case.

```markdown
# <주제> — 외부 시선 검토

## 대상·의도
<범위, 렌즈 수, 리뷰어에게 준 것과 주지 않은 것>

## 판정: 통과 | 이견 | 반대
<한 줄 요약. 높은 심각도 지적이 없으면 통과, 있으나 렌즈끼리 갈리면 이견, 합치되면 반대>

## 지적
| # | 심각도 | 렌즈 | 지적 | 리드 판정 | 근거 |

## 규칙 재검토 후보
<해당 항목만. 없으면 "없음">

## 리뷰어가 문제없다고 본 것
<1~3개. 적대적으로 지시받은 리뷰어가 넘긴 부분이라 그 자체가 정보다>
```

문서는 `docs/`에 두고 **git add·커밋하지 않는다**(untracked 유지, 자동 스테이징 훅도 `docs/`는 제외한다). staged 됐으면 `git restore --staged <문서>`로 되돌린다. 작성한 md 경로를 응답 마지막에 출력한다.
